# 多设备固定分单与结果回传

## 目标与可回溯基线

本任务实现固定清单分配、独立工作机采集、可靠回传和控制台统一进度。原有主采集、发文和费用的浏览器操作流程继续复用，不调整点击节奏。

- 已验证基线提交：`f67e1f280e9ca2443d0d3365b795146a61e5267d`。
- 稳定标签：`stable/2026-09-26-before-multidevice`。
- 开发分支：`codex/multi-device-collection`，使用独立工作树。
- 新版版本号：`2026.09.26 r0`，本次只提交功能分支，不合并到 `main` 自动更新源。
- 基线验证：818 项测试、278 个子测试通过，10 项跳过；同一申请号发文及费用实测成功。

标签保护程序版本；数据库、坐标和登录配置的备份独立于 Git。新功能只增加协作任务表，不移除既有专利列，旧版本仍可读取既有业务数据。回退前须停止协同采集，并保留工作机尚未回传的任务目录。

## 日常操作

### 1. 准备两台电脑

两端都安装本分支版本，各自完成原有 Chrome、代理证书及坐标校准。保存主数据库的完整备份后，在主库电脑的 `data/machine_role.txt` 写入 `master`；其余工作机继续使用 `replica`，无需改成 master。每台电脑保留自己的坐标、登录与工作机身份文件。

首次验收建议两台电脑，每台分 3 至 5 件。主库只负责分单也可以；如果主库电脑还要参与采集，把它也列为一台设备并在本机接单。同一电脑同时运行一个桌面任务，原有单机采集入口仍可使用。

当前开发使用独立工作树，原桌面图标仍指向原来的稳定版目录。安装候选分支前先停止该目录的采集和后台，并保留未提交文件。已有 Git 安装可在原项目目录操作：

```bash
git fetch origin
git switch -c codex/multidevice-preview origin/codex/multi-device-collection
uv sync --frozen --extra desktop --python 3.11
```

开发电脑也可使用已存在的本地 `codex/multi-device-collection` 作为新分支起点。不要强制切换或清理 `data/`。未推送或没有网络时，可从已验证的代码分支另行部署，不能用 `main` 的 HTTP 更新按钮取得本候选版本。

### 2. 让工作机连到主库

桌面图标自动启动的后台仅监听本机。需要先停止主库旧后台，再在主库项目目录启动允许局域网接入的控制台：

```bash
uv run --frozen python web_dashboard.py --host 0.0.0.0 --port 8765
```

随后可打开原桌面图标接入同项目后台，或在主库本机访问 `http://127.0.0.1:8765/#distribution`。关闭桌面控制台仍会停止它连接的后台和本机任务。主库后台退出期间，其他工作机已采成果保存在本地，稍后重传。

工作机照常打开本机控制台，主库地址填写例如 `http://192.168.1.10:8765`。两端网络需要互通，主库防火墙允许该端口；跨网络可使用已有的可信组网地址。远程访问主库页面只能查看，分单和复制任务码必须在主库本机操作。任务码只授权对应任务，不包含管理员权限。

### 3. 分单、接单和确认

1. 主库打开「多机协同」，选择案件状态、发文或费用，填入申请号和设备名称。每次最多 500 个申请号、8 台设备，每台至少分到一件；发文、费用的申请号必须已经在主库建档。
2. 点击「平均分单」，在列表中为各设备分别「复制任务码」。分配按设备固定，不会自动在电脑之间抢单；同类型的未完成目标不能重复分配。
3. 对应工作机填写主库地址和任务码，点击「开始本机采集」。程序自动启动任务专用代理和采集 Chrome；在官网登录、完成验证码后，按原流程点击控制台的登录完成按钮。采集期间保持电脑唤醒、Chrome 前台可操作。
4. 工作机在任务日志中显示采集与回传进度；主库列表的「成功」才代表成果已确认入库。「本机已处理」包含失败和中断，「主库已确认」也会细分成功、失败、中断、冲突，不能把交付件数当成成功件数。
5. 对失败、中断、冲突或撤销后未成功的申请号使用主库「重分未成功项」，检查清单后重新分配。费用每轮每件一次；失败回传进入现有费用失败清单，后续成功会清除。冲突项先核对主库已有信息，再决定是否重采。

任务码只交给对应工作机；程序存入本机私有配置文件，后续恢复无需重复输入。若要替换执行电脑，撤销旧任务并对尚未成功的项目重新分单。

### 4. 断网、停止与重试

| 情况 | 操作及结果 |
|---|---|
| 初次领取前主库无法连接 | 保留已登记任务；恢复连接后点「继续接单」，无需再粘贴任务码。 |
| 已采集，但回传时断网 | 点「重传结果」，只发送封存成果，不再次操作 CNIPA。 |
| 主库已保存，工作机未收到确认 | 重传返回原收据，不重复写入、不重复累计费用失败。 |
| 停止任务或异常退出 | 已有批次封存后回传；未完成项记为中断，再由主库分配。异常退出后若仍显示采集中，可尝试恢复回传；仍存活的采集进程持有互斥锁时会拒绝操作。 |
| 主库已撤销任务或拒绝凭据 | 显示「主库拒绝接收，请检查分单」并保留原因与本地成果，不再提示反复重传；在主库检查后重新分单。 |
| 同栏目在分单后已被主库更新 | 标记冲突，不覆盖主库新值。其他栏目的变化不阻止回传。 |

撤销只停止后续接收，已确认的数据保留；在线工作机通过后续进度请求发现撤销后停止，断网期间不能立即收到撤销。不要删除 `data/worker_tasks/` 或 `data/worker_id.json`，前者包含尚未交付的成果，后者绑定原任务的设备身份。

已在控制台登记的任务也可用命令行恢复。将占位文字替换为 32 位任务编号，命令自动选择任务目录：

```bash
uv run --frozen python distributed_worker.py run --task-id TASK_ID
uv run --frozen python distributed_worker.py deliver --task-id TASK_ID
```

`run` 仅在尚无批次时启动采集；已存在批次时只封存和回传。`deliver` 始终只回传，不启动浏览器。

## 首版边界

主库机使用 `master` 角色，工作机保留各自角色。主库按申请号和采集类型分配互不重叠的固定清单，每台工作机同时执行一个桌面任务。首版支持 `main`、`fwxx`、`fees`；暂不自动抢单、扩缩容或修改同账户请求节奏。

主库控制台创建分单并生成仅能访问该任务的任务码。工作机填写可访问的主机地址和任务码，通过现有控制台启动任务、完成人工登录；任务码不出现在命令行或日志中。主库列表显示已分配、运行进度、已确认成功、失败、冲突和取消状态。

## 数据与事务归属

分单和确认记录属于主库 `PatentsDB`。创建任务在事务内核验同类型目标没有未完成的分配，并冻结本领域字段基线。详情任务必须已经在主库建档。

工作机每个任务拥有 `data/worker_tasks/<task_id>/`，其中数据库和代理缓存完全独立。机器坐标、桌面锁、登录确认标志继续共享本机固定路径，防止两个任务争抢桌面；代理和采集器使用同一个任务目录及专用代理端口。工作机不把主库的旧发文、费用等整行快照复制进任务数据库。

工作机以持久批次的逐件状态作为完成依据；只有成功项从任务数据库提取对应领域白名单。任务结束或中断后封存交付文件，断网后只重传原文件，已经采到的记录不重复采集。未完成和失败项保留原因，不冒充业务成功。

主库每项接收在一个 SQLite 事务内完成：核验任务凭证、设备归属和目标，检查基线，更新本领域字段，保存幂等收据。重复内容返回原确认，变更内容拒绝；取消任务不能继续写入。主库对应领域在分单后已有新修改时记录冲突，不覆盖新数据；别的领域变化不影响接收。费用空列表表示无记录，缺字段或 null 不视为完整采集。

## 外部接口

- 本机管理：`/api/distribution`、`/api/distribution/assignments`、单项 invitation/cancel、`/api/distribution/worker-tasks`。
- 工作机领取：`GET /api/worker/assignments/<task_id>`，返回 `{assignment: ...}`。
- 工作机进度：`POST /api/worker/assignments/<task_id>/progress`，接收 state、completed、succeeded、failed。
- 工作机交付：`POST /api/worker/assignments/<task_id>/results`，每次接收一项 `{protocol_version, application_no, status, fields, reason}`，返回 `{receipt: ...}`。
- 工作机认证头：`X-CNIPA-Task-Token` 与 `X-CNIPA-Worker-ID`。只为上述精确路由授权，不授予管理员权限。
